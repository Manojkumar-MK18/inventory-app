How to read this document

Each expandable section lists the screens and their fields. “Key” means the suggested database/API field name. “Type” is the suggested data type. “Required” indicates whether the field should normally be mandatory. Adjust names and rules to your implementation.

Important clothing-inventory rule: stock must be tracked at variant level (for example, Shirt / Black / XL), not only at product level. Every sale, purchase, return and stock adjustment must update the exact variant.

A · Shop Registration

First screen · Owner only
In simple words: This is the very first thing that happens. The shop owner creates an account, enters the shop details, and the system automatically makes them the Owner and creates the first branch. Nothing else in the app works until this is done.

Step 3 — What the system creates automatically
  1. A row in shops with the details above.
  2. A default branch in branches named “Main Store” (is_default = true).
  3. The default roles (Owner, Manager, Cashier, Sales Staff, Stock Manager, Accountant) for this shop in roles.
  4. A shop_memberships row linking the registering user to this shop with the Owner role.
  5. A membership_branches row giving the Owner access to the Main Store.
  6. Default settings (low-stock alerts on, negative stock off, return window 7 days).
All of this must happen in one database transaction. If any step fails, nothing is saved, so you never get a shop without an owner.

Use composite unique keys such as UNIQUE(shop_id, invoice_no) and UNIQUE(shop_id, barcode) so two shops can both have invoice #1 without clashing.

Multi-shop isolation rules
  1. shop_id is NOT NULL on every business table.
  2. The server takes shop_id and branch_id from the session, never from the browser form.
  3. Every query includes WHERE shop_id = :session_shop_id. Put this in one shared data-access layer so nobody forgets it.
  4. Extra safety (PostgreSQL): turn on Row-Level Security so the database itself blocks cross-shop reads.
  5. Foreign keys must stay inside the same shop (an invoice of Shop A cannot point to a customer of Shop B).
  6. Index (shop_id, branch_id, created_at) on big tables like invoices and stock movements for fast reports.
  7. Data export and backups are per shop, so an owner can download only their own data.
Example: Ravi logs in and picks Shop B. His session holds shop_id = B and role = Manager. Every list, report and bill he sees is filtered to Shop B, and his Manager permissions apply — even though he is Owner in Shop A.

Cross-module rules that must be implemented

  1. Stock ledger: every purchase, sale, return, exchange, damage and manual adjustment creates a traceable stock movement.
  2. Audit trail: record actor, timestamp, action, record ID, before/after values and reason for sensitive changes. Do not allow staff to edit or delete audit logs.
  3. Approval workflow: high discounts, invoice cancellation, refunds, price overrides and stock adjustments require configurable manager/owner approval.
  4. Financial accuracy: totals, tax, discounts, payment allocations and balances should be calculated on the server, not trusted from the browser.
  5. Data integrity: use unique invoice numbers, SKU/barcodes, database transactions and referential links to original invoices/purchases.
  6. Security: role-based access, hashed passwords, session expiry, backups and restricted exports.
  7. GST: configure tax rules according to the store's registration and product classification; validate with the store's accountant.
Specification starter — field names and data types are proposed design suggestions, not a prescribed legal/accounting schema. Confirm GST, invoice and retention requirements with the business accountant before production.
